# Phase K Execution Plan

Phase K strengthens release and compatibility infrastructure before the next
large platform feature phase. Execute it in small, mergeable slices. Each slice
should leave the workspace shippable and should tighten one public contract.

## Current Starting Point

The repository already has a clean baseline for Phase K work:

- `tests/fixtures/conformance.tsv` is the authoritative compatibility matrix.
- CLI, Python, and WASM entry points expose public analysis and runtime output.
- CI runs Rust format, clippy, tests, Python wheel tests, and WASM target checks.
- Public runtime JSON is still assembled separately in CLI and WASM, while the
  Python binding maps the same runtime result into Python dictionaries.
- Golden JSON snapshots, output schema versioning, and benchmark gates are not
  yet established.

## Rules for Every Slice

- Keep public output changes intentional, documented, and fixture-backed.
- Do not mark a feature `supported` or `partial` unless at least one fixture
  backs the claim.
- Prefer shared output helpers over duplicating JSON or dictionary mapping logic
  across CLI, Python, and WASM.
- Run the full release verification gate before closing a slice.
- Update this document as implementation details become concrete.

## How to Use the Acceptance Criteria

The exit criteria under each slice are local merge criteria for that slice. The
Phase K closeout checklist is the stage gate for moving the main roadmap to
another phase such as Phase E, F, or I.

Phase K should not be marked complete until every closeout checklist item is
done or explicitly moved into `docs/PHASE_K_AUDIT.md` as a non-blocking
maintenance tail. Maintenance tails should be narrow, documented, and should not
weaken the three long-term Phase K acceptance criteria:

- New feature work cannot accidentally widen compatibility claims without
  conformance metadata.
- Public output changes are intentional and documented.
- Performance regressions are visible before release.

## Slice 1: Public Output Schema Versioning

Goal: give every public output shape an explicit version and a single source of
truth.

Steps:

1. Add a public schema version constant, for example `PUBLIC_OUTPUT_SCHEMA_VERSION`.
2. Decide the shared ownership boundary:
   - Prefer a runtime-owned or small shared crate helper if CLI, Python, and
     WASM all need the same data shape.
   - Keep host-specific conversion code thin.
   - If shared runtime serialization is deferred to Slice 2, still put the
     schema version constant in the intended shared contract location now so it
     does not need to move later.
3. Add `schemaVersion` to CLI `run` output.
4. Add `schemaVersion` to CLI `analyze` output if the analyze command emits a
   machine-readable shape.
5. Add `schemaVersion` to CLI `matrix --format json` output.
6. Add `schemaVersion` to Python `analyze_script` and runtime result
   dictionaries.
7. Add `schemaVersion` to WASM `analyzeScript`, `runScriptCsv`, and
   `Program.runCsv` JSON strings.
8. Add tests that assert each public entry point includes the same schema
   version.
9. Update `docs/CONFORMANCE.md` with the versioning rule.
10. Update `docs/ARCHITECTURE.md` with the shared output ownership boundary.

Exit criteria:

- CLI, Python, and WASM expose the same schema version value.
- Existing consumers can identify the output contract version.
- Public output version tests fail if one binding forgets the field.

Verification:

```text
cargo fmt --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace
cargo check -p pine-wasm --target wasm32-unknown-unknown
maturin build --manifest-path crates/pine-python/Cargo.toml --out dist
python3 -m pip install --force-reinstall dist/*.whl
python3 -m pytest python/tests
```

## Slice 2: Shared Public Output Serialization

Goal: remove drift between CLI and WASM JSON, then keep Python field mapping in
lockstep with the same model.

Steps:

1. Inventory the current public output fields for:
   - Runtime results.
   - Profiled runtime results.
   - Analysis results.
   - Compatibility matrix JSON.
2. Extract shared JSON helpers for runtime output before changing field names.
3. Replace CLI runtime JSON construction with the shared helper.
4. Replace WASM runtime JSON construction with the shared helper.
5. Keep Python conversion explicit, but add tests that compare top-level keys
   with the shared runtime output contract.
6. Decide whether analysis and matrix serialization should also move into the
   shared helper in this slice or a later slice.
7. Document any intentionally host-specific fields.

Exit criteria:

- CLI and WASM runtime JSON are generated by the same code path or by a clearly
  shared contract helper.
- Python exposes the same top-level runtime result fields as the shared output
  contract.
- Tests cover top-level keys and at least one nested output family such as
  `plotShapes` or `plotCandles`.

Verification:

```text
cargo test --workspace
cargo check -p pine-wasm --target wasm32-unknown-unknown
maturin build --manifest-path crates/pine-python/Cargo.toml --out dist
python3 -m pip install --force-reinstall dist/*.whl
python3 -m pytest python/tests
```

## Slice 3: Golden JSON Snapshots

Goal: make public output changes visible in review.

Steps:

1. Create `tests/snapshots/` for checked-in public output snapshots.
2. Add a small snapshot test harness that:
   - Runs a fixture.
   - Normalizes output deterministically.
   - Compares against the checked-in JSON snapshot.
3. Start with high-value runtime snapshots:
   - Basic `plot(close)`.
   - Marker outputs: `plotchar`, `plotshape`, and `plotarrow`.
   - Bar/candle outputs: `plotbar` and `plotcandle`.
   - Color outputs: `bgcolor` and `barcolor`.
   - `hline` and `fill`.
4. Add analysis snapshots for at least one supported script and one unsupported
   feature.
5. Add a matrix JSON snapshot for `pine-compat matrix --format json`.
6. Document the snapshot update workflow.
7. Keep the first snapshot harness strict. Add tolerance handling later only if
   a real numeric stability issue requires it.

Exit criteria:

- Changing a public field name, omitting `schemaVersion`, or changing matrix
  JSON structure fails a snapshot test.
- Snapshot files are small enough to review.
- Snapshot update instructions are documented.

Verification:

```text
cargo test --workspace
```

## Slice 4: Conformance Metadata Gate

Goal: prevent compatibility claims from growing without fixture metadata.

Steps:

1. Harden TSV validation for `tests/fixtures/conformance.tsv`:
   - `feature` must be non-empty and unique.
   - `status` must be one of `supported`, `partial`, or `unsupported`.
   - `notes` must be non-empty.
   - `fixtures` must contain at least one path.
   - Every fixture path must exist.
2. Add status-specific fixture rules:
   - `supported` and `partial` entries should have runtime, sema, syntax, or
     regression fixture coverage appropriate to the feature.
   - `unsupported` entries should have unsupported or sema diagnostic coverage.
3. Ensure all built-ins in the supported registry are represented in the matrix
   with the expected status.
4. Ensure known unsupported platform families remain represented.
5. Add tests for malformed rows, duplicate feature names, invalid statuses, and
   missing fixture paths.
6. Keep the matrix command derived from the same validated metadata.

Exit criteria:

- New feature claims fail tests unless conformance metadata is complete.
- Duplicate or malformed matrix rows fail tests with clear messages.
- Matrix JSON remains fixture-backed and snapshot-covered.

Verification:

```text
cargo test -p pine-cli
cargo test --workspace
```

## Slice 5: Release Verification Entry Point

Goal: make local release checks and CI checks use the same command list.

Steps:

1. Add a single verification entry point, preferably `scripts/verify.sh`.
2. Include the release gate:
   - `cargo fmt --check`
   - `cargo clippy --workspace --all-targets -- -D warnings`
   - `cargo test --workspace`
   - `cargo check -p pine-wasm --target wasm32-unknown-unknown`
   - `maturin build --manifest-path crates/pine-python/Cargo.toml --out dist`
   - `python3 -m pip install --force-reinstall dist/*.whl`
   - `python3 -m pytest python/tests`
3. Make the script fail fast and print the command being run.
4. Update CI to call the same command or keep job-specific commands documented
   against the same canonical list.
5. Update `README.md` development verification instructions.
6. Document prerequisites for Python and WASM checks.

Exit criteria:

- A contributor can run one documented command before opening a release PR.
- CI and local release verification do not drift silently.
- The script works on Linux without extra shell-specific dependencies beyond
  standard POSIX shell behavior.

Verification:

```text
scripts/verify.sh
```

## Slice 6: Performance Benchmarks and Profile Fixtures

Goal: make performance regressions visible before release.

Steps:

1. Choose the first benchmark mechanism:
   - Start with profile fixture tests if avoiding new dependencies is preferred.
   - Use Criterion only if stable benchmark reporting is worth the dependency.
2. Add deterministic benchmark/profile fixtures for:
   - Long histories with `ta.sma`, `ta.ema`, and `ta.macd`.
   - Many stateful callsites.
   - Array-heavy scripts.
   - Dynamic history offsets and `max_bars_back` behavior.
3. Record metrics that already exist in `RuntimeProfile` before adding new
   counters.
4. Decide which checks are hard failures and which are informational.
5. Keep CI hard thresholds conservative to avoid noisy failures.
6. Document how to run benchmarks locally.

Exit criteria:

- Long-history and many-callsite behavior has repeatable local measurement.
- At least one CI-visible check catches severe allocation or runtime growth.
- Performance documentation distinguishes expected variability from release
  blockers.

Verification:

```text
cargo test --workspace
```

Run any benchmark command added by this slice and document the exact command in
`README.md` or this file.

## Slice 7: Release Documentation and Phase K Audit

Goal: close Phase K with published compatibility and release rules.

Steps:

1. Update `docs/RELEASE_NOTES.md` with:
   - Current supported subset summary.
   - Schema version rule.
   - Compatibility matrix source of truth.
   - Known unsupported boundaries.
2. Update `docs/CONFORMANCE.md` with snapshot and matrix maintenance rules.
3. Add `docs/PHASE_K_AUDIT.md` when the implementation is complete.
4. In the audit, record:
   - Completed slices.
   - Verification commands and results.
   - Remaining maintenance tails.
   - Recommended next phase.
5. Update `docs/LONG_TERM_EXECUTION_PLAN.md` if Phase K scope or exit criteria
   changed during implementation.

Exit criteria:

- Release notes, conformance docs, schema version, snapshots, and matrix output
  agree with each other.
- Phase K has a closeout audit similar to previous phase audit documents.
- The next implementation phase can start without relying on unstated release
  assumptions.

Verification:

```text
scripts/verify.sh
```

If `scripts/verify.sh` has not been added yet, run the full command list from
Slice 1.

## Recommended Execution Order

Use this order unless a discovered blocker requires reordering:

1. Public output schema versioning.
2. Shared public output serialization.
3. Golden JSON snapshots.
4. Conformance metadata gate.
5. Release verification entry point.
6. Performance benchmarks and profile fixtures.
7. Release documentation and Phase K audit.

## Phase K Closeout Checklist

Complete this checklist before using Phase K as the completed foundation for the
next major roadmap phase. If an item is intentionally deferred, record the
reason and risk in `docs/PHASE_K_AUDIT.md` before closing Phase K.

- [x] All public outputs include `schemaVersion`.
- [x] CLI and WASM runtime JSON share one output contract.
- [x] Python output is tested against the same public contract.
- [x] Golden JSON snapshots cover representative runtime, analysis, and matrix
      outputs.
- [x] Conformance metadata validation rejects malformed or unbacked claims.
- [x] A single release verification entry point is documented.
- [x] CI covers Rust, Python wheel, WASM target, snapshots, and metadata gates.
- [x] Performance/profile coverage exists for long histories and many
      callsites.
- [x] Release notes describe the supported subset and unsupported boundaries.
- [x] `docs/PHASE_K_AUDIT.md` records closure evidence and the recommended next
      phase.
