## A：完成内容

- 四个线程池（指标、Pyne 等待、在线存储、数据准备）统一有限准入。底层线程池只接收固定数量的执行循环，业务等待项放在可移除的队列里，取消不会留下持续增长的占位项。
- 总准入上限为 `workers + pending`。外部请求满额时立即拒绝；数据准备内部只有受 worker 数量限制的任务和生命周期操作可以等待容量。没有给任意 HTTP 请求新增无限等待队列。
- 诊断保留原字段，补充 `max_pending`、`max_inflight`、`queued`、`cancelled` 和 `rejected`。未开始的取消任务会被实际移除，`pending` 在任务结束后归零。
- 存储操作在开始执行后，即使调用方反复取消，也会等到操作返回或抛错后再传播取消。指标计算取消后仍计入物理容量，直到线程真正结束。
- 保留 `contextvars` 跨线程传递，避免丢失发布预算等调用上下文。
- 数据准备服务的数据库读写、启动恢复、租约、调度检查、检查点、库存核对、取消、重试与 READY/错误写入都经过独立存储线程池。`submit/cancel/retry` 改为 async，生产调用方及原有测试同步适配。
- HTTP 侧的日志查询、缓存管理、策略上下文和历史范围读取也经过该边界。服务关闭会等待已经接纳的请求写入，随后释放租约。
- 共享下载的所有权加入/退出受保护，防止新增异步等待后，一个任务加入正在取消的下载，或者新下载的引用被旧任务清理。
- 任务终态和“库存需要重扫”在同一 SQLite 事务中提交；扫描持有代次，旧扫描不能把更新后的库存误报为 READY。没有修改数据库表结构。
- 数据准备 API、行情查询错误映射及应用未捕获的容量异常返回 `503 / EXECUTOR_BUSY / Retry-After`。指标保留已有批次逐项响应协议，用 `EXECUTOR_BUSY` 和可重试字段说明满额。

## B：完成内容

原问题是 `_persist_bar_event` 把磁盘异常、SQLite 锁冲突和正常来源质量拒绝都折叠成 `False`，随后不更新缓存、不发布事件，外层 callback 还可能吞掉错误。本阶段把这些情况分开处理。

- 默认 SQLite 存储新增 `bar_delivery` 接收/发布日志和 `bar_delivery_watches` 源数据恢复范围表。原 K 线表、来源优先级和序列身份契约保持兼容。
- 最终行情先保存不可变接收记录（`pending`）；写入 canonical K 线与把记录改成 `committed` 在同一事务中完成。事务中途失败会一起回滚，接收记录仍然存在。来源质量拒绝是独立的 `rejected` 状态。
- 一个发布任务按日志序号处理记录。只有 canonical 提交后才更新缓存、交给事件总线，交接成功后标记 `published`。暂时写入失败保留记录并重试；`accepted` 表示已有可靠接收记录，不代表全部消费者执行完毕。
- 单次存储调用最多尝试 3 次；后台任务继续处理可恢复记录。接收请求最多同时 64 个，未完成日志最多 4096 条，终态记录按最近约 8192 个序号保留。满额会明确失败，不新增无限内存等待队列，未完成记录不因清理终态日志而删除。
- 如果连接收记录都无法保存，抛出 `BAR_DELIVERY_UNAVAILABLE`；BarAggregator publisher 和 ingestion 的核心回调路径继续向上传递它，不再当作普通观察者错误吞掉。
- 启动物理行情流之前先保存恢复范围；保存失败则流启动返回错误。范围向前覆盖聚合器的闭合 bar 内存窗口（默认 500 根，可随原配置调整），遇到更早的历史修正会在接收前扩展。异常退出或接收失败后，通过现有 BackfillCoordinator 重新读取权威源，并要求 `completed`、连续性核验成功且无错误，才删除恢复任务。不能完成核验时保留范围及诊断。
- 事件标识在重试和重启中保持一致；每个订阅队列有限保存最近已接收的标识，避免确认写入失败后同一个事件重复进入该队列。字段快照保留完整精度、增强成交指标、previous bar 和 provider/venue 等语义身份。
- 已提交事件的发布恢复会核对当前 canonical 行；如果已有更高质量的修复，发布当前修正值，避免旧日志把冷缓存回退。canonical 行已经被明确删除时，不从日志复活该行。
- 关闭时先停止行情生产，再停止发布/恢复任务；追踪并取消接收中的异步任务，等待已开始的物理事务结束。即使关闭自身反复被取消，也不会先释放恢复范围。尚未发布的持久化记录留给下次启动。
- DataManager 快照、健康诊断和 bar provider 诊断补充 `bar_delivery`：模式、待处理量、当前批次恢复范围数、失败原因、接收失败标记、接收并发量和拒绝次数。

主要实现入口：`data_manager/bar_delivery.py` 管理异步生命周期、重试和源补取；`storage/bar_delivery.py` 管理 SQLite 原子操作；`aggregator_bridge.py` 负责聚合事件转换及提交后的缓存/总线交接。

## C：完成内容

故障回归先复现了 9 个失败场景：同一 feed 上先调用 `commit: none`，后调用 `commit: active`，两者共享整个“请求并提交”Promise，后者也得到 `committed: false`。history、before、range、latest 四条路径都有这个问题；后加入者的取消信号也没有自己的生效位置。

- 移除 SeriesDataFeed 外层的整流程 Promise 去重，删除已无生产调用者的 `InflightRegistry` 及其旧测试。四种读取都由 `SharedKlineRequestCoordinator` 统一负责传输共享。
- SeriesDataFeed 收到现有工作台协调器时直接复用；收到原始 KlineApi 时，按适配器对象复用一个协调器，避免默认回退和自定义适配器绕过独立取消契约。工作台关闭 broker 功能时也保留这项正确性边界，但仍禁用批量 HTTP、指标 broker 和原有受该开关控制的调度功能。
- 每个调用者都有自己的 Promise、AbortSignal、commit/source、指标窗口所有者、epoch 和实时修正校验状态。取消第一个或后加入者都只结束自己的等待；最后一个所有者离开才取消物理请求。提交回调抛错也不会拒绝其他调用者的结果。
- 去重键保留会影响服务端结果的参数、完整行情身份、需求 scope/generation，并加入客户端读取代次、修复 scope 和实时版本边界。新会话及实时修正之后的读取不会加入旧快照。客户端上下文在进入真实适配器前移除，不写入 HTTP 查询或批量请求体。
- range 的每页 HTTP 可以共享，但分页上限、游标推进、取消、提交和完成状态仍由每个调用者管理。不同指标窗口所有者分别获得自己的提交元数据。
- 去重发生在申请调度名额之前。因此即使调度器只有一个槽位，同步请求也不会被串行化成两次相同 HTTP。排队发起者取消或图表卸载时，其他所有者可以接手；较高优先级的前台调用者可以提升尚未开始的共享请求。
- 调度器支持移除已取消的排队项；已经取得执行槽位的操作仍由原完成路径释放跨窗口预算。前台保护租约按逻辑调用者持有和释放，不会由一个调用者提前结束其他人的保护。
- 保留每批最多 16 项的历史读取；批次内失败按条目分发。同步抛出的批量适配器异常也会结算所有等待者，随后可以重试。旧物理请求晚返回时不能清掉新请求的注册项。

## D：完成内容

原阻塞点是订阅队列满后，`DataEventBus.emit()` 等待 `put_lossless()` 腾出容量。一个迟迟不返回的回调会使后续发布也停住。本阶段保留每个订阅的独立任务，移除发布者对消费者队列容量的等待。

- 每个订阅队列默认最多 1000 项；共享进程内重放窗口默认最多 8192 项，两者都要求正数，0 不再意味着无限容量。`BAR_UPDATED` 和 `PRICE_UPDATED` 是可替换预览，其余生命周期、收盘、修正和完成事件进入重放窗口。
- 队列满时，优先回收可替换预览；没有可回收项则记录该消费者的重放起点。生产者和其他消费者继续推进。该消费者排空已有队列，再按序读取共享窗口，期间新到达的可靠事件也从同一窗口接续。过滤仍使用完整 SeriesKey 和事件类型。
- 重放窗口耗尽，或回调抛错时，订阅进入终止性的 `recovery_required`，不继续发送普通事件。迭代器抛出 `CONSUMER_RESYNC_REQUIRED`；回调订阅通过独立的恢复通知任务得知缺口，即使原回调仍挂起也能收到通知。每个订阅最多一个这样的任务；通知失败保留错误诊断。
- 总线快照补充进程 epoch、窗口容量/用量、确认序号、最近确认的 B 阶段 delivery id、重放起点/次数和恢复原因。`backpressured` 保留为兼容字段且恒为 0，实际切入重放次数使用 `replay_entries`。不能用旧 epoch 的内存游标跨进程续传。
- 使用 B 阶段稳定的 delivery id 避免发布确认重试产生重复分发。可靠事件在入窗口时复制，交给消费者时再隔离副本，回调修改收到的对象不会损坏其他消费者的重放内容。
- 关闭时取消并等待消费者任务及恢复通知任务。恢复处理器即使先取消了自身订阅，也仍在总线任务登记中，不会因脱离订阅表而逃过关闭清理。

实际消费者的处理：

| 消费者 | 窗口之外的恢复行为 |
| --- | --- |
| K 线 WebSocket（单周期、多周期、批量） | 关闭连接，使用 `1013 / CONSUMER_RESYNC_REQUIRED`。多周期 outbox 不再忽略可靠事件入队超时；批量原有满队列关闭策略继续保留。 |
| 浏览器 K 线 | 断开时为已持有的闭合历史范围建立恢复检查，并推进客户端读取 epoch。重新订阅确认后重读该范围；只有完整、连续、无待修复缺口且覆盖原有行的结果才能解除恢复状态。每次最多 20 页，单个恢复流程运行，失败每 10 秒重试；当前周期未核验通过时继续显示重新同步。 |
| 内置指标 | 旧增量状态失效，保留订阅所有者引用计数；范围缓存清空并更换 revision epoch，旧计算请求和续传游标随之失效。通知 WebSocket 重连后从 canonical 历史重新预热。重新建立 bridge 失败时保留 `recovery_failed`，拒绝把旧实例或新订阅报为可用。 |
| Pyne 指标 | 释放受影响的订阅运行状态并要求连接重同步。指标客户端收到显式重同步关闭码后去掉旧 resume cursor，要求完整快照。 |
| 指标发送队列 | 满队列优先驱逐预览；可靠队列仍满则写入一个终止标记，触发重同步，不再为每个可靠消息创建阻塞入队任务。 |
| 告警 | 记录可见的恢复状态并停止后续求值，不自动补发可能重复的外部副作用。停用再启用后，必须取得 complete、无缺口、不可重试且含闭合 bar 的 canonical 快照才能重新订阅；旧于该预热时点的排队事件不再制造交叉告警。快照不可核验时保留等待诊断，由既有协调循环重试。 |
| 插件 K 线 | 将上游缺口接入既有 `resyncRequired` 终止协议；释放订阅，再由插件重新读快照及订阅。 |
| ingestion 非核心队列、BarAggregator 迭代队列 | 可靠事件溢出时明确终止并抛出恢复异常，不在缺口之后继续交付原始增量。BarAggregator 的形成中更新允许丢弃。满队列关闭也能唤醒迭代器。核心有序回调仍按既有事务契约等待。 |

## D：确认边界与恢复限制

1. B 阶段 `published` 仍只表示交给总线，不能当成消费者处理完成。D 的 `confirmed_sequence` 表示回调正常返回，或迭代器请求下一项；回调若只是交给下游工作任务，这仍是本地交接确认。WebSocket、插件和指标任务继续承担各自的下游成功/失败协议，没有跨进程 exactly-once 承诺。
2. 8192 项窗口是进程内的有限恢复能力。超出窗口或进程重启后，恢复依据是 B 已提交的 canonical 数据及既有源补取能力，而不是伪造连续消费游标。没有向 SQLite 写入原始高频成交或订单簿增量。
3. 终止的订阅没有“跳过缺口并恢复正常”的开关。必须重新取权威状态并建立新订阅。指标 bridge 若连重建都失败，诊断要求先修复依赖并重建数据运行时。告警重新预热不追补停滞期间可能出现的历史通知。
4. 浏览器保留窗口若超过单次页数限制、数据仍待补齐或原有行无法在权威快照中验证，会持续显示恢复状态；不会凭一次重连或最新价格更新宣称历史已经恢复。
5. 隔离针对协作式 asyncio 消费者及有限队列，不会把任意同步 CPU 工作或阻塞 I/O 自动搬到其他线程。本阶段没有生产压测、真实行情源断流演练或浏览器人工交互验证。
