# 冷历史按交易对统一回填（Family Fill）设计

状态：第 0 步已实现并测量（§7、§9）；FamilyFill 待实现
范围：Binance USD-M，冷启动时自定义周期（mixed composition）图表的历史回填
相关：`backfill/mixed_plan.py`、`data_manager/backfill_scheduler.py`、`data_manager/custom_query.py`、
`storage/revisions.py`、`storage/native_history_fence.py`、`storage/mixed_history_fence.py`、
[H127](HISTORY_BLOCK_READER_H127.md)、[MIXED_HISTORY_H127](MIXED_HISTORY_H127.md)、
[KLINE_REVISION_CONTRACT](KLINE_REVISION_CONTRACT.md)

## 1. 问题

同一交易对的多张图同时冷加载时（典型：89m、97m、101m、10007m），每张图各自切成 16 个目标一块的 chunk，
每个 chunk 独立完成"规划 → 取源数据 → 写源数据 → 派生 → 写派生"，靠乐观并发和写入校验保证正确。

实测（四图冷加载，`BENCH_LIVE=closed_once`，记录见 `output/cold-local-cost-20261119/README.md`）：

- 一次加载写约 6.2 万行，读约 25.4 万行（2,643 次读取）：reconciler 读组件窗口 12.3 万行，
  `reuse_committed_minutes` 5.8 万行，mixed 规划的 `known_inputs` 5.9 万行。
- 真实实时写入下每次加载约 32 次冲突。10007m 一次加载里，13 次成功尝试共 23 秒工作时间，
  7 次冲突重新规划和 2 次重试共 115 秒。
- 冲突来源是结构性的：
  - 多张图在重叠时间段各自取同一批源数据，路线不同（一个走月度归档、一个走 REST），后写的写入校验失败；
  - 一张图写入更细的数据（如 1m），会让其它图在同一时间段基于较粗数据的规划或派生失效（细数据优先）；
  - 归档对象（整天/整月）写到计划窗口以外，让其它图的粗粒度区间只被部分覆盖，无法合成。
- 已试过并撤回的三种协调：规划前刷新读取基准、在途获取登记板、按目标区间加锁。前两种没减少关键冲突
  （登记板失败的原因是冲突写入来自计划窗口以外的可选父批次归档对象）；加锁把冲突降到接近零，但串行化让
  总时间变长（全部就绪 24–25 秒 vs 不加锁 19–25 秒），并出现新的 PARTIAL（越界写入的细数据挡住粗区间）。

**本设计的上限。** 用一个预先存好全部源数据、没有派生数据的库做"只派生"加载（`pairs/r6`，负载 3.5–4.5，
四轮配对）：

| | 全部就绪（中位数） | 进程 CPU | 首次出现 K 线 |
|---|---|---|---|
| 冷加载 | 28.2 秒 | 33.6–49.0 秒 | 89m/97m/101m 3.4–10.4 秒，10007m 11–26 秒 |
| 只派生 | 23.6 秒 | 24.0–44.4 秒 | 四图 16–30 秒 |

源数据全部在库并没有明显更快，首次出现反而晚得多。原因在读取路径：源数据在库时，10007m 由图表请求
在请求里合成（`DataManager.query_composed` 每次加载约 15 秒 CPU），但一次加载要合成 3–4 次，只有最后一次被采用。
前几次都被要求"整个交易对的所有 series 都没变"的检查作废，包括页面以外的最新一分钟写入（§7）。

所以，只把源数据统一获取，最终状态就是"只派生"，收益很小。本设计的收益来自两部分：

1. 读取路径一页只合成一次、一次落库（§7，第 0 步，已实现）。这一部分不依赖 Family Fill；
2. 源数据按交易对统一获取（§3–§6），去掉冲突重做的工作，并让派生按最新优先逐段进行。

## 2. 目标与非目标

目标：

1. 同一交易对的冷历史需求（一次或多次请求、一张或多张图），每个时间段的源数据精度只决定一次，
   每个源数据窗口只由一个写入者获取一次。
2. 一个时间段的派生，在该时间段的所有源数据写入（含越界的归档对象）提交之后才开始。
3. 最新的可视区优先：每张图首屏所需的范围最先完成源数据、派生和发布。
4. 不放宽任何写入校验（native/derived/mixed fence、删除权限、K130）。冲突消失的原因只能是
   受管范围内没有并发写入者，而不是校验变松。
5. 任何一步失败或超时，都退回现有 chunk 流程，结果与今天一致。

非目标：

- 不改实时流、增量修复、手动修复、向左拖动时的增量补齐（继续走现有 chunk 流程）。
- 不改读取路径的数据规则，只改"何时不在请求里现算"（§7）。
- 不改交易所限流和网络并发策略。
- 不降低派生本身的计算量（"只派生"的进程 CPU 中位数约 35 秒，扣除读取路径约 15 秒后仍有约 20 秒，另行处理）。

## 3. 总体结构

```text
图表请求（每张图一个 RepairRequest，不变）
        ▼
BackfillCoordinator / BackfillScheduler
        │  合格的冷 mixed 请求 → 登记到其交易对的 FamilyFill（新）
        │  chunk 照常生成；目标范围与未提交分片的写入范围重叠时不派发（门控，§6）
        ▼
FamilyFill（每个 (exchange, market_type, symbol, identity) 至多一个活动实例）
   1. 汇总：该交易对所有待处理合格请求的 chunk
   2. 统一规划：每个 chunk 用现有 mixed planner 只规划不执行；合并后，用 planner 自己的
      细数据优先逻辑求不动点（§4）；按选中的归档对象确定每个分片的实际写入范围
   3. 获取：最新优先，每个分片作为普通原生修复交给 BackfillEngine（§5）
   4. 释放：分片提交后，唤醒与之不再有未提交分片重叠的 chunk
        ▼
被释放的 chunk（现有流程）
   规划时源数据齐全 → plan.tasks 为空 → 只派生、只写派生（与今天"只派生"加载的路径相同）
```

FamilyFill 只做"规划 + 源数据获取"，不做派生，不产生 RepairOutcome。请求的生命周期、进度事件、
gap ledger、需求租约、取消、缓存回读，仍由现有 chunk 负责。

## 4. 统一规划

### 4.1 输入

FamilyFill 收集该交易对满足以下条件的待处理请求：

- 带 `required_history_composition` 或 `bounded_history_batch_contract`；
- 默认 identity、`AlwaysOpenCalendar`、Binance USD-M（与 `mixed_history_fence.capture_targets` 的合格范围一致）；
- 规划显示目标范围存在缺失源数据（冷）。

对每个 chunk 的目标范围调用 `build_mixed_backfill_plan`，只取结果、不执行：

- `plan.derived_source_windows`：完整覆盖所用的全部源数据窗口（含已存在部分），按精度给出；
- `plan.tasks`：其中需要获取的部分。

规划在只读的 acquisition scope 里进行，不捕获任何写入校验。规划被拒（`_DeclineMixed`，如超出行数或请求预算）
的 chunk 不接管，照常走现有流程。

### 4.2 细数据优先的不动点

合成规则：库里已有的更细的 canonical 数据（即使只是部分，也包括不在合成路线里的周期，例如 3m）优先于较粗的
原生 K 线，并且细化会替换**整个** span（不是单根 bar）。因此统一规划要保证：

> 获取完成后，每张图的每个目标，按 planner/reader 的真实规则选出的覆盖，只用到"已存可信行 ∪ 本次获取行"。

不另写一套单元级算法，直接复用 planner 的细化逻辑（`plan_fixed_range` / `_MixedBackfillBuilder.refine`），
在假设的存在集合上求不动点：

```text
presence = 库里已有的行
planned  = ∅
repeat:
    needed = ∪ 每个 chunk 的每个目标：在 presence ∪ planned 上按 planner 规则求出的覆盖所需的行
    missing = needed − presence − planned
    planned ∪= missing
until missing = ∅
```

每轮只会让覆盖变细（新增行只能是更细精度触发的细化），而精度只有有限几级（路线为 1m、5m、15m、1h、4h、1d），
所以几轮内收敛。代价是多取一些细数据。常见情形下这部分本来就要取：最近两周短周期图要的 1m 很密，
10007m 在这段时间本来就会因细数据优先而改用 1m（实测一次 128 根的合成读 4.7 万行源数据，最近两周全是 1m）。

`needed` 里被更细数据整段替代的粗行，不再获取。

### 4.3 归档对象与写入范围

路由（`HistoricalSourceRouter`）选中的归档对象总是按整天（1m 日度文件）或整月（1h 月度文件）对齐，
写入范围可能超出 `planned`。做法：

1. 统一规划完成后，对全部分片做一次路由（含父批次预取），得到选中的对象；
2. 把每个对象的完整范围并入 presence，再跑一轮 §4.2 的不动点；新增的缺口并入获取计划；
3. 执行时，分片只写自己声明的对象和窗口，不再临时预取声明以外的对象（登记板方案失败的直接原因）。

对象按天、按月对齐，它覆盖的 1h/4h/1d 区间都是完整的，第 2 步通常不新增获取。

## 5. 获取（单写入者）

### 5.1 分片

- 分片边界取归档对象的边界（天、月）和各图首屏范围的边界；一个对象只属于一个分片。
- 每个分片的**写入范围** = 其各精度窗口 ∪ 其归档对象的完整范围。
- 顺序：首屏范围所在的分片优先，然后由新到旧。

### 5.2 执行

每个分片作为普通原生修复交给现有 `BackfillEngine`（`intervals=[g]`，范围为该精度的窗口，对象已在路由阶段确定），
复用现有路由、限流、内存准入、native fence 和 reconciler 的原生写入路径，用它自己的 acquisition
（与任何新开始的原生修复相同）。写入范围不重叠的分片可以并发（受现有网络与内存准入限制）。

### 5.3 写入校验

不修改任何校验。分片照常在获取前捕获 native view，写入时检查。受管范围内仍可能让它失败的只有：

- 实时流写入最新已收盘的 1m（每分钟一次，只影响最新的分片）；
- 不受 FamilyFill 管理的写入者（手动修复、其它进程）。

失败照常重试该分片：重新核对已有行，只取剩余部分。

## 6. 门控、释放与新需求

### 6.1 门控条件

调度器 `_drain` 里，chunk 派发前已有同类检查（`_series_conflict`、`_shared_gap_input_active`：
跳过、留在就绪队列、不占内存和配额）。新增一个：

> chunk 的目标范围 `[start, end + duration)` 与本交易对任一未提交分片的**写入范围**重叠时，不派发。

必须按写入范围而不是计划窗口判断，原因有两个，都在代码里：

- 源数据行的插入会触发 `kline_dependents_*`（`storage/revisions.py`），删除与之重叠的派生 K 线。
  已派生的区间如果之后被别的分片的越界对象写入，刚发布的 K 线会被删掉。
- mixed 派生写入的校验 `MixedComputation.check`（`storage/mixed_history_fence.py`）拒绝
  `[target.start, target.end + duration)` 内、在计算开始之后的任何源数据变化。

反过来，这个校验只看范围：基于 1,024 个修订以内的 block receipts，或每个 series 的范围链。
所以较旧分片在不重叠的范围里继续写入，不会让已释放 chunk 的派生失败。这是"边获取边派生"成立的前提，
验收时要确认 `mixed_receipt_suffix_unavailable` 为 0。

### 6.2 释放

分片提交后，FamilyFill 更新"未提交写入范围"，调度一次 `_drain`。被释放的 chunk 走现有流程：
规划时源数据齐全，`plan.tasks` 为空，只派生和写派生。它的 mixed target view 和 computation head
都在相关源数据提交之后捕获。

### 6.3 新需求加入

FamilyFill 运行中来了同一交易对的新合格请求（另一张图打开，或首屏以外的更多历史）：

- 新请求的 chunk 照常进入门控；
- 对新目标增量规划：并入 `planned` 重新求不动点，只把新增获取加入待执行分片；
- 已提交的分片不重做。新图需要更细的精度时，只追加获取细数据，由细数据优先生效，不删除已写入的粗数据。
  注意：追加的细数据插入会删掉与之重叠的已发布派生 K 线（§6.1），这些目标会由重新门控、重新派发的 chunk 重建。
  这与今天打开新图时的行为相同。

### 6.4 失败与回退

- 某分片在重试上限内仍失败：把它的写入范围标记为"回退"，释放重叠的 chunk，由它们按现有流程自己获取。
- 一段时间（例如 60 秒）没有进展，或进程关闭：释放全部门控，回退到现有流程。
- 任何回退都等价于今天的行为，正确性由现有校验保证。

### 6.5 取消

请求取消时，其 chunk 照常被取消。FamilyFill 只执行仍被至少一个活动请求覆盖的分片；无人需要的未开始分片直接丢弃。

## 7. 读取路径：一页只合成一次、一次落库（第 0 步，已实现）

本节最初的设想是"后台回填期间读取路径不现算"。逐次追踪合成后更正如下：

- 冷加载里，读取路径的合成几乎不花 CPU（每次加载 32–43 次调用，共 0.4–0.9 秒）：源数据不全时，
  它在计数探测阶段就退出。
- "只派生"加载里没有 10007m 的 chunk，读取路径就是唯一的派生者。它一次加载把 10007m 合成 3–4 次，
  只有最后一次被采用。一次追踪（负载约 4）：
  1. 两次合成（2.1 秒、3.0 秒 CPU）作废，原因是"precedence/publication view changed"：合成全程持有一个
     B130 view，任何一个源 series 的版本变化都会让它失效，包括页面范围以外的最新一分钟写入
     （实时流、短周期图的 chunk）；
  2. 第三次合成成功，但落库走 family 级 `Acquisition.check`（没有范围证明时的兜底），
     同一交易对任一 series 在查询期间有写入就失败；
  3. 结果采用（`revision_checked_query` 的 `consumer.conflicts`）也是 family 级，同样会丢弃结果；
  4. 第四次才落库，10007m 在 14.4 秒就绪，而第一次合成在 2.5 秒就已完成。

三处检查都要求"整个 family 不变"，而一页只依赖自己范围内的数据。改为
（`data_manager/mixed_query.py`、`storage/mixed_history_fence.py`、`custom_query._try_mixed`、
`data_manager/revisions.py`）：

1. **每批一个 view**：每 32 个目标一个 view。每批在 view 内用 `check_store_range` 证明它的读取范围
   （向前多看一个最粗精度的宽度）自查询的 floor 以来没有变化，所以整页等价于在 floor 上用一个 view 合成。
   一批被打断时只重做这一批（最多 3 次）。
2. **落库用范围证明**：合成前捕获 `MixedTarget`（目标窗口指纹、删除权限）；落库时在 `computation_scope` 里用
   `MixedComputation`（revision = floor）检查，与 backfill 派生用的是同一种范围校验。
3. **采用用范围证明**：结果带 `ClosedMixedRead`。采用时先用范围证明；失败时退回原来的 family 级检查。
   它被拒绝的变化同时也是 family 级的变化，所以只会多采用，不会少采用。
4. **隔离**：证明放在 acquisition 的 `read_targets` 里，backfill 的捕获和原生写入都不看它；只有
   `_try_mixed` 设置的 `computation_scope` 能用它授权写入。

有回填 chunk 时是否还要"不现算"，留到 FamilyFill 再评估：现在一页最多被读取路径合成一次，
与 chunk 的重复工作有上限，并由 `custom_materialization_registry` 的租约避免重复写入。

## 8. 正确性要点

- 写入校验不变。受管范围内冲突消失，是因为没有并发写入者，且派生的校验在相关源数据提交之后才捕获。
- 不动点用的是 planner 自己的细化规则，归档对象的完整范围也已并入，派生时不会遇到"粗区间被部分细数据覆盖"。
- 门控按写入范围判断，已发布的派生 K 线不会被受管的源数据写入删除。
- 分片是普通原生修复，有自己的 acquisition；chunk 保持自己的删除权限下限。分片若删除了行（原生修复语义），
  重叠的 chunk 照常因删除权限检查失败并重试，与今天相同。
- 所有回退都回到现有流程，现有测试覆盖的行为不变。

## 9. 预期效果与验收

第 0 步实测（`pairs/r11-derive`、`pairs/r11-cold`，同一棵树开关交替，各 4 轮，
`BENCH_LIVE=closed_once`，`net_zero`）：

| | 全部就绪（中位数） | 进程 CPU（中位数） | 10007m 就绪 | 10007m 合成 |
|---|---|---|---|---|
| 只派生，第 0 步 | 7.5 秒 | 11.2 秒 | 5.2 秒 | 每次加载 3 次，2.1–2.7 秒 CPU |
| 只派生，原来 | 13.9 秒 | 18.5 秒 | 13.9 秒 | 每次加载 4–5 次，8.1–9.9 秒 CPU |
| 冷加载，第 0 步 | 15.8 秒 | 21.6 秒 | 15.8 秒 | |
| 冷加载，原来 | 21.1 秒 | 28.6 秒 | 21.1 秒 | |

只派生负载约 4–5；冷加载负载 5–9，且后两轮原来一侧负载更高，冷加载的差值只能算"不变差、可能更好"。
冷加载的改善主要在短周期图（89m/97m/101m 就绪 8–9 秒 vs 11–14 秒），原因尚未逐项追踪。

据此估算：

- 第 0 步之后，"只派生"比冷加载快约一倍（7.5 秒 vs 15.8 秒）。这个差距就是 FamilyFill 能拿到的上限：
  去掉冲突重做（10007m 115 秒的废弃工作时间），让冷加载接近"只派生"。
- 剩下的是派生本身（"只派生"约 11 秒 CPU，负载 4–5），要达到每图 3 秒还需另行降低派生成本。
  测量与两处削减见 `DERIVE_ONLY_CPU_zh.md`（种子库过期和适配器启动使这个数字偏高；修正后快模式约 5 秒）。

验收（`bench_audit.py` 四图，`BENCH_LIVE=closed_once`，配对交替，负载尽量 ≤ 2）：

第 0 步（已满足）：

1. "只派生"库上首次出现 K 线提前：10007m 5.2 秒 vs 13.9 秒，短周期图 5.9–6.8 秒 vs 10.7–11.7 秒；

- 测试：`tests/test_family_fill.py`（门控、按月放宽、按（精度, 月）分片、分片不合并、被门控的 chunk 不派发）、
  `tests/test_family_fill_pipeline.py`（真实协调器、引擎和存储上两张冷图：开启时每行源数据只取一次且全部来自分片，
  图只派生；关闭时照常完成；规划失败或分片过慢时释放，图自行取数完成）。
- 第一轮基准暴露出三处开销，已修：
  1. 分片太多（90 个，每个都是一次完整的原生修复）。现在 1h 及更粗的需求按整月取 1h（整月 1h 是一个归档对象，
     4h、1d 随之不再需要）；更细的只取连续的长窗口（至少 360 格）和 chunk 边界一天内的窗口（按整天取，
     否则相邻 chunk 会导入同一天的对象）；短的边缘分钟留给需要它的 chunk 在同一次运行里取。每个分片至多 4,000 行，
     由新到旧，最多 4 个同时进行。一次冷加载 24 个分片。
  2. 被门控的请求每次轮询都会重排全部 chunk。现在兴趣没有变化时（同一缺口再次提交）合并不再重排就绪队列。
  3. 规划期间首屏被门控。现在先规划每张图最新的 chunk，它们的分片完成即释放（规划 0.3 秒，分片约 2 秒内完成），
     其余 chunk 之后再规划。
  另外：只规划时与先前分片的写入或内存冲突，按 chunk 重试，仍失败则该 chunk 自行取数，不再放弃整个 fill；
  `choose_cold_sources` 是纯函数，结果缓存，chunk 释放后的规划不再重复计算。
- 配对结果（`pairs/r13-fill`，开关交替 3 轮，`closed_once`，负载 6–9）：

  | 中位数 | 开 | 关 |
  |---|---|---|
  | 四图全部就绪 | 36.6 秒 | 25.4 秒 |
  | 进程 CPU | 48.5 秒 | 34.9 秒 |
  | 首次出现 K 线（89m/97m/101m） | 2.5/2.8/2.9 秒 | 6.4/5.3/4.4 秒 |
  | 首次出现 K 线（10007m） | 4.3 秒 | 13.1 秒 |

  首屏明显提前，但全部就绪变慢，CPU 多约 40%。分片的每 1,000 行都是一次完整的引擎运行（准入、校验捕获、路由、
  写入、ledger、缓存回读），fill 在图自己的运行之外又加了约 100 次；冲突重做省下的不够抵消。
  加大并发（8 个分片）和每次运行 4,000 行在单次运行里都更慢（全部就绪 42.9 秒、68.5 秒），已撤回。
- 只做首屏（其余 chunk 不门控，`pairs/r14-first`，负载 6–18，噪声很大）：首屏没有提前，CPU 更高，已撤回。
  首屏的提前来自门控其余 chunk、把 CPU 让给首屏，而不是来自统一规划本身。
- 结论：在每次引擎运行的固定开销降下来之前，FamilyFill 不划算，开关保持默认关。
  更值得先做的是降低每次运行的固定开销，它对现有流程和 FamilyFill 都有利。
