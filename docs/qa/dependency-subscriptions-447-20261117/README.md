# #447 补齐依赖订阅：并发需求、共享输入与下层资源背压

本次实现来自用户确认的职责划分：新需求立即分析依赖，复用合格 canonical 数据、订阅在途输入，仅为剩余范围创建物理获取。HTTP、交易所配额、存储执行器和内存 owner 决定实际执行容量。

## 实现

- coordinator/scheduler 默认 `max_concurrency=0`，取消上层整段下载→计算→写入的全局槽、同系列互斥和本地派发 token。独立父需求及同父需求拆出的独立范围均可同时分析和订阅；单个物理页的分页顺序仍由交易所分页合同控制。正值显式配置保留有上限的嵌入行为。
- `HistoricalFetcher` 原 owner 内维护短期输入订阅簿。所有 adapter 只共享相同物理请求；已资格化的 Binance spot/USD-M、固定 UTC 网格、闭合原生历史页额外支持重叠范围切片及剩余区间获取。身份、market、字段投射、finality、transport 绑定和原始删除许可均参与匹配；未知合同不做范围切片。
- HTTP 槽缩到实际页请求；已有 exchange gate、公共配额与冷却继续生效。订阅者可以提高共享输入的有效优先级；一个消费者取消不会撤销其他消费者需要的输入，最后一个释放后才取消物理获取。
- 物理页预算在 HTTP 执行槽内取得，字节保留到现有 writer 采用。流式采用逐页释放，普通有界批次跨本地修订重试保留成功输入；完成回执仍受 source journal 当前版本及事务内提交围栏约束。过期输入退出匹配簿，新获取只覆盖缺失部分。
- 内存临时不足交回执行槽、等待预算 owner 的释放通知，取消可撤回，不消耗普通失败次数；本地容量等待仍计入净耗时。超出固有上限的申请和无容量句柄的错误继续明确失败。
- 明确可重新规划的 canonical 内容变化和修订回执过期单独延期重做读取，不耗尽网络/普通失败次数；原许可、身份和 owner 失效不属于此类重试。混有普通获取错误时仍按普通失败处理。
- 刷新读取视图不刷新原始删除许可。同父并发范围共享首次许可；每个范围分别释放，全部范围退出后才执行一次父请求最终确认。保留修订、删除、字段缺失与数值合同。
- 订阅簿仅保留在途/待采用输入，有条目及订阅上限；没有新增持久缓存、下载器、配额账本或 writer。新增诊断区分逻辑输入任务、成功物理页、共享订阅、剩余区间、容量等待及失效回执；这些累计计数不作为墙钟扣除项。

## 证据边界

- 四轮均为独立无行情种子的 macOS profile，UI preferences 仅配置 89m/97m/101m/10007m、EMA20/60 与 frontend-JS close；真实 Binance USD-M。保留相同已验证 frontend/desktop ASAR 和 Python runtime/plugins，覆盖完整当前 backend 并严格核对签名。属于保留 runtime 的原生候选，不是全新 release 构建。
- driver 是有界冷库诊断，不是 #463 的十分钟/切换/隐藏恢复/保存重启完整矩阵。360 秒只是本次观察长度，不替代验收门槛或新增总耗时限制。原始失败保留，不能拼接不同版本通过项。
- 净耗时仍按 #447/#463 原合同：仅扣有关键路径证据的交易所通信/下载和限流，实际总耗时独立记录；本地调度、资源等待、计算、提交、修订重试、UI 采用全计入。缺少完整每图物理关键路径时保留 `null`，不扣累计 fetch。
- 第一、二轮执行时 driver 尚未进入其产品提交；`driverSourceCommit` 是工作树基线，实际执行原文由回执 `driverSha256` 和本目录文件核对，不能声称能从这两个旧提交取出 driver。最终候选同时提交 driver。
