## 改动与硬边界

默认混合 consumer 以最多 **32 个目标桶** 预排实际 span，把同一细来源的存在性检查合并到
repo 所有的 `query_bars_range_presence`：每次最多 **256 个半开范围**、一条 SQL、完整来源身份、
有序 bool 回执。它检查所有 provenance，包括不可信/不完整的细记录，不把存在性当作最终性证明。

工作索引最多 4096 个范围，计入原 `history-query` owner 的 4MiB 预留，下一批清空；
初始计划搜索另用有界临时预留，不同时保存大量 target 计划。没有新全局缓存、writer 或修订表。
未触及的来源、或最早 open 已在 span 之后的来源不需要探测。
粗来源失败后的细化 span 未命中工作索引、或 storage 不提供可选批量接口时，保留原 limit=1 探测。

所有查询、bool 回执和目标页仍处于同一个 D126/B130 来源版本 view 下；
探测期间发生修订或删除不能发布/物化旧页。范围数量、字段类型或回执数量不合法也不能赋予粗来源资格。
默认公共预算和 H127 页上限没有提高；额外工作受原 owner admission 限制，预算不足仍明确延期。

复核时另补一个正确性边界：旧细记录的 `close_time < open_time` 时，持久变更的 close-based 上界
未必包含其实际 open。不能用该上界略过存在性/删除检查；当前只用可靠的最小 open 排除 span 之后的来源。
因此一些陈旧删除会保守地阻止更多粗块，转向原细来源，而不是声称无缺口。

受控真实 SQLite 复现：在第二个 89m 目标内，写入一个 `3m/open=99m/close=0` 的不可信细记录，
再由离线 SQL 物理删除，经过原 D126 trigger。#367 默认入口错误地返回 complete 并物化 1 根；
产品返回 incomplete、物化 0 根。原始记录和复现脚本 `malformed-finer.py` 在本目录，
数据均为隔离 fixture，没有改动用户库。

小周期完整分钟路线仍为 3 次规范 SQL，目标物化快路径仍为 1 次。

不包括版本轮询和 SQLite 内部页 I/O。批量探测返回的 bool 是 scalar SQL 结果，
`mixed_presence_rows` 不能当成 candle 行；总 `storage_rows` 包含这些结果，故不以它宣称行情解码下降。
各次返回 reserved=0，B130 leases/views/inflight/retired=0；来源分钟行数未增加，缓存上限未提高。

## 耗时结果不能作为稳定提速验收

本机新 consumer/临时 DB、已写入官方录制行情，OS 缓存非冷，tracemalloc 开启，每组 n=3。
最初探索产品 `09b9c590f80f15b8c4924c296657d012bb4c022d` 的 89/97/101m 未物化中位数为
837/825/844ms，基线为 1210/1004/1060ms。但最终产品复跑为 **2374/1693/1409ms**，
10007m 混合为 449ms、完整分钟为 5458ms，也慢于基线 285/3792ms。
未改动的目标物化快路径从约 14ms 同时升至 21–41ms。

复跑后快照观察到系统 StorageManagement/ApplicationsStorageExtension/Xprotect 的高 CPU；
这是运行环境不受控的迹象，**不能证明其覆盖全部试跑、也不能把回归数值删除或直接归因于它**。
没有终止用户/系统进程来取得好看的数据。三轮完整原始回执都保留；
本批只证明正确性和物理查询次数下降，**不认定稳定 wall-clock、P95/P99、RSS 或原生首屏提速通过**。
需后续冻结环境或交错配对测量，继续保留 #127 的性能关闭条件。
