# 常驻策略有界结果索引

基于 Draft #250；应用提交 `e790c4f7a994e49b4a06079a7df1ecaadf8b9c72`。本层为私有持久化和读取边界，还没有默认应用绑定、公开 HTTP/WS 或三模式界面。

## 结果和财务提交

Schema 3 新增 `result_heads` / `result_items`。账户检查点、游标、结果摘要及新增/变更条目在同一财务 SQLite 事务提交，最后仍由 Manager 来源保护把关。初次账户创建还包括原创建意图的原子提交。

新增结果编码在来源写保护之前完成，准备包由冻结的 JSON 字符串、元组和账户归属组成；短事务内只发布已准备的结果和检查点。没有增加逐事件全历史哈希或全量结果重写。现有恢复检查点仍保持原来的完整状态编码，本 PR 不声称消除了那部分已有成本。

已检查 Kernel 的实际变更规则：fills、decisions、rejected、账户 journal、order_events、frozen_intents、fill_source_events 取新增尾部；订单仅重读上次仍为 OPEN/PARTIAL 的索引；权益曲线允许替换最后一个采样点。既有活动条目内容不变时不重复写入。此处沿用合格 Kernel 的追加/尾部变更合同，不对旧历史做重新扫描或逐事件防篡改校验。

当前账户权益/未实现盈亏复用现有 `ContractAccount` / `SpotCashAccount` 的方法，仅传入已提交余额、持仓、入场价、标记价和乘数标量；不恢复 journal 或执行订单。它们与 `latest_equity` 的最近曲线采样点分别返回。现货、V1 永续多/空和稀疏采样反例均验证与实际执行账户一致。

## 有界读取与版本

- 摘要最多 32 KiB；单条最多 256 KiB；每页最多 200 条，按编码字节预算不超过 1 MiB。先查询轻量条目元数据，只取本页字节预算容纳的 wire。
- 完整集合按零起始索引分页；变更读取按 `(changed_revision, kind, index)` 对当前条目去重合并，不是不可变的逐笔事件日志。
- 一次读取事务把 run、摘要、counts 和本页绑定到同一 SQLite 快照；不选择恢复检查点 wire、Provider 状态或策略源代码。
- 后续页必须带完整初始 identity。若财务或控制版本已变，返回明确冲突，调用者刷新；这里没有旧版本分页租约或隐式跨版本拼接。后续订阅/界面须遵守这一边界。
- 活动订单查询显式使用局部索引；首轮测试发现 SQLite 会自行选择扫描所有订单的主索引，已修正查询，保留原失败和最终实际执行计划验证。

## 空间与迁移

结果 payload 加每行 256 字节、摘要 1024 字节的保守索引预留，与检查点共用现有总预算。计数按准备增量维护；预算检查只汇总有界账户/检查点行，不扫描全部结果。该预留不是 SQLite/WAL 实际物理文件大小的逐字节承诺。

Schema 1/2 升级仅创建空索引表，不改动原 run、定义或检查点。对旧账户显式 `ensure` 时，在写保护外解码一次旧检查点准备索引，最终再次核对财务版本；并发新提交、磁盘预算或写入失败均保留原财务状态。正常创建/续跑自动与新检查点发布索引。无法识别为合格账户的旧恢复数据保留，明确不提供结果资格，不伪装成另一种账户。

版本升级后的数据库使用 Schema 3；旧版 Store 不认识该版本。本 PR 没有删除账户、回退 schema 或自动重置来源的操作。

## 验证

- `results-final.log.gz`：相关策略、财务、来源保护、执行器、Manager、应用关闭、历史账户回归 **319 passed / 5 既有 warnings / 0 skipped**，不是全仓测试。
- 其中 28 个结果场景包括分页/增量重建、活动订单更新、日收盘末点替换、稀疏权益、精确十进制值、当前估值、跨进程读取、WAL 并发提交、初次和续跑结果写入失败、来源确认回滚、旧数据预算不足、并发旧索引准备及响应字节预算。
- SQLite authorizer 实际拒绝 checkpoint 表和定义字段的读取时，结果读取仍通过；全新解释器也直接读取原索引。结构场景拒绝迭代/索引已处理历史，验证仅新尾部、旧活动订单和曲线末点被读取。它们证明组件合同，不是完整产品或延迟 SLO。
- 首轮 `results-focused.log.gz`：19 通过、1 失败，失败是上文的实际查询计划；修正后保留了 36、40、315、27 项中间验证，最终 319 项通过。
- 架构检查仍返回既有 10 项，与 main 基线逐字节一致，见 `results-final-architecture.log.gz`。

本轮未运行前端全检查（前端未改）、未组装/启动原生包、未调用公开行情，也没有 Windows 产品验收。CI 在后台执行，合 main 前核对最终 head。下一步为 Manager/应用生命周期绑定、带上述版本边界的公开创建/结果订阅和控制接口，以及三模式界面；已有财务结果的历史修复仍需独立授权流程。
