# #177 提交后账户状态第一阶段

基线 main #217/87d670bb，包含已合格的 #212 通知基础设施。没有重建撮合引擎，没有改动单向/现货撮合、费用或资金公式，也没有把只读真实账户事实并入模拟账本。

## 选择和实际范围

沿用既有 TradingAccountService/TradingStore 与 PracticeRuntime。HTTP 控制和读取进入 DataManagerCore.trading；行情仍由现有 PracticeRuntime 经 DataManager 消费。提交后唤醒复用 shared committed_updates，不另建行情协调器或财务事件账本。

每个连接先给完整替换快照，后续只在提交/成功应用估值后唤醒并合并读取。快照的资金、订单、交易和笔记使用同一只读 WAL 世代；每次组合投影只读取并重建一次 fills。数据库持久 epoch/sequence 与写入同事务回滚；连接自有 epoch/sequence 另外排序未落盘估值，不能假装它是持久游标。原先无成交游标每10秒刷盘策略保留，未通过增加每tick写库获得及时显示。

前端沿用每账户共享数据 owner。面板和固定账户图表共用一条流，最后消费者释放后取消，旧回调隔离；写后显式刷新获取晚于确认的新完整快照。模拟账户取消原2秒/15秒状态轮询；手工账户没有模拟盘行情租约，保留15秒快照重验证，避免估值停更。连接静默30秒后退出并重连。笔记读取失败保留已有笔记并显示错误，不阻挡有效资金/持仓。

## 账本读取开销测量

measure_projection.py 使用临时真实SQLite和当前正式服务函数，比较原summary/trades/journal三次读取与新account_state一次组合快照；输入是相同已平仓账本，无网络、HTTP/UI或撮合性能结论。三个规模各5次交替测量，完整视图相等：100笔交易P50 5.55→2.59ms，1000笔43.66→16.24ms，5000笔230.70→85.83ms；fills读取/重建均3→1。此结果不含行情输入/renderer、活跃持仓/复杂笔记或多订阅压力；不能代替资源/原生验收。新增关闭接线后10项流/应用关闭检查再次通过。
