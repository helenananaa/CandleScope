## 修复和验证的问题

1. **缺口的部分修复被再次修订或删除。** 原严格订阅保留第一次修复的副本，
   后续完成缺口时可能回放旧值或已删除的数据。现在替换重复时间戳的修复值，
   并在完成缺口前重新核对整个有界缺口的持久数据。通知尚未到达的落库修订
   也能被读到；已删除的部分修复明确触发 `source_gap_revision_changed`。
2. **OKX 历史回补丢弃有效收线。** 真实桌面冷启动和真实断流同时复现：
   `trades`/taker 字段为 null，转换器调用 `int(None)` 后丢弃完整 OHLCV。
   修复后只在内部算术结构中使用占位值，资格掩码确保 SQLite 和公开结果仍
   保留未知字段的 null。现货与永续均通过真实 fork 解析、回补、SQLite 回读。
3. **OKX REST 客户端缺少已声明的 2d/3d。** WebSocket 已支持 UTC 周期，独立
   REST 池仍使用 CCXT 默认表，原生 3d 报 `unsupported CandleScope timeframe`。
   REST 使用同一已资格化映射的基础值，由 pinned fork 添加一次 UTC 后缀；
   16 个真实 pinned 方法测试覆盖现货/永续和 6h–3M，核对 bar 及范围参数。
4. **历史补洞误终止下一根自然收线。** 原生 forming bar 在补洞之前捕获修订，
   补洞完成后它的自然收线被整个序列的修订号拒绝。现在只在同一 SQLite
   事务内证明完整原生 bar 与持久、终身合并的变更范围不相交时允许继续。
   不提升 acquisition revision；重叠变更、空范围/全范围删除、派生依赖仍
   走拒绝及恢复路径。后来的不相交写入不能掩盖早先的重叠修改。
5. **最新 Pine 主线的测试接口变化。** 更新两处旧夹具以接受 execution options
   和确定的执行时间，纳入三个分支的 CI 选择器。旧的 Windows 测试命令拆分
   与 main 冲突时采用主线完整实现，保留 10 项脚本回归。

6. **重连绕过分阶段加载。** 真实四图 5d 失败现场及 CDP 请求证实，WebSocket
   重连反复申请每图 1500 根，首屏 128 根补洞被合并进更大历史任务。恢复现在
   以首屏计划和已持有深度为依据，500/1500 的已有窗口保留，未满首屏不扩展到
   全历史；仍遵守来源行预算，正常后台扩展继续由 hydration 路径负责。

7. **REST 历史重复进入实时交付。** 原生 4d 超时现场出现 1643 个待交付 receipt；
   历史回补写入 canonical 后，来源 receipt 仍未确认，重启 pipeline 把过去的
   历史再次送入实时聚合，引发大量版本拒绝和重连。FetchedBar 现在保留来源引用，
   只有当前原生 REST revision 成功写入同一 SQLite 事务才一并确认；失败、回滚、
   过期来源及 WebSocket 交付仍保持待处理。真实 fork 的现货/永续回补回归覆盖
   写入后的 pipeline replay。随后原生重启又发现退出时取消的后台补页尚未落库，
   其来源也不能成为实时收线：现在由 Backfill 请求在来源观察中持久标记 history
   owner，实时启动仅回放 market owner。被取消历史的证据和未确认 revision 保留，
   由后续历史查询/修复重试完成；不伪造已交付，WS/冲突校准 REST 仍可正常回放。
   无 owner 的旧记录继续保持旧行为，不猜测或改写其来源用途。

以上实际缺陷均保留修复前失败证据。另补充两项 canonical 回读期间修订/删除
回归：现有强制 revision sync 已正确处理该竞争，这两项不是新产品修复。
