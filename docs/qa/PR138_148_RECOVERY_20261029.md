# PR #138 / #148 revision-delivery recovery

The composed deferred-receipt failure is fixed. A repair may advance the durable
revision before a queued final receipt is dispatched. The fence must still reject
that old write, but affected consumers must explicitly resnapshot and subscribe
again instead of silently waiting for the missing close.

## Changes and ownership

- #138 code: `8299ad5fc25c1cd90299172833ec6385c5fbd64c`, based on `afd02956`.
  The rejection transaction persists `bar_delivery.recovery_required=1`. Pending
  counts/admission and pruning protect that receipt until the dispatcher hands
  recovery to the EventBus and acknowledges it. Retry/reopen preserves the
  handoff; one subscription receives at most one terminal notification.
- Exact-series and wildcard bar consumers receive `source_revision_superseded`.
  Callback notification is independent of a blocked data callback; iterators wake
  without another market event. Different symbols, periods, semantic identities
  and subscriptions interested only in unrelated event types remain live.
- Deleted canonical rows, including deletion between journal commit and cache
  adoption, use the same recovery path. No rejected payload is replayed or written
  back. Ordinary source-quality arbitration does not invalidate a consumer.
- #148 code: `48d8a0abb2c4985c2270973a58c2a744ebb5ec70`, based on `d0c073c2`.
  Source-gap replay checks terminal state before each remaining bar. An in-flight
  callback can finish, but it cannot be followed by more replay callbacks after
  recovery is required. The original deferred-receipt regression now covers both
  callback and iterator consumers, preserving its delivered-prefix assertion.
- Both PRs include the durable-delivery, revision, subscription and consumer
  recovery tests in the existing CCXT CI selector. The two PRs remain independently
  applicable to `main`; neither branch absorbs the other feature's implementation.
