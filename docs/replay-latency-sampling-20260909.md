# 回放连续采样结论（2026-09-09）

结论：空仓的主要明显重复工作已减少，但持仓推进仍存在结构性成本，尚不能称为优化收尾。下一轮应针对持仓命令的事务边界和重复账户状态构建，而不是优先做更多 React 微调。

## 环境与口径

- 基于 `47efca20` 加工作区已有的原子收尾/相同 HEDGE 标记跳过写入修改；本轮没有修改产品实现。
- 克隆当前训练数据库、数据对象、账户输入和历史缓存。独立后端 18082、前端 15175；原本的 18080/15173 服务和训练记录不参与测试写入。副本原为 HEDGE 空仓，测试通过 UI 建立 0.001 BTC、10x 模拟多仓，随后通过 UI 平仓。
- 相同 BTCUSDT 15m 展示周期、1m 基础数据，MACD/VOL 两个指标与账户侧栏。样本沿历史向前推进，不是同一历史区间的随机交叉 A/B；不能把不同阶段的速度差全归因于某一个改动。
- 132 次手动推进：开发空仓 32、开发持仓 32、生产持仓 32、生产页面重载后首次推进 4，以及明确置前后的生产持仓/空仓各 16。另有三段自动播放和独立服务剖析各 5 次。
- 请求耗时来自 Resource Timing；图表与指标耗时从捕获阶段真实 click 到图表 series 数据更新事件。不是显示器像素实际呈现耗时。132 次均记录到成功响应及 MACD 三条线、VOL 一条线的更新。
- 页面请求处于热系统环境。四次“重新加载”不代表 OS、磁盘、服务端缓存全部冷启动。其样本量不足以给出稳定长尾结论。

主图在响应之后的数据更新很快，各组中位数约 1–4ms。开发模式的指标延迟明显更高，但生产模式下持仓请求依然昂贵。

最慢的持仓请求约 6,003ms，其中 `replay_sql_commit` 累计约 4,694ms；它不是一次 SQLite commit 的耗时，而是该请求中所有被计时提交的总和。其余持仓请求也经常在 1 秒以上，因此不能仅归因于这一次磁盘尖峰。

空仓最慢约 522ms，服务端推进约 497ms，但其提交与工作线程计时没有解释整个余量。不能把这部分未经单独剖析的时间直接归因于网络或某一个后台任务。

## 持仓结构性成本

分别从空仓、持仓数据库副本启动独立 ReplayService，执行五次 DISPLAY_BAR，使用同一方法包装器统计实际调用次数。方法时间有嵌套与测量开销，不能相加当作总耗时。

| 每次“下一根 15m” | 空仓，5/5 次一致 | 持仓，5/5 次一致 |
| --- | ---: | ---: |
| 适配器推进命令 | 1 | 15 |
| 数据库写事务调用 | 5 | 47 |
| `_component_state` 调用 | 10 | 93 |

后续补充计数澄清：这里是函数调用次数，不能等同于实际重新构建次数。Actor 已有快照缓存；持仓对照中每次推进实际 `reducer.snapshot` 构建为 15 次，其余为缓存访问。后续优化和报告按实际构建次数区分。

独立服务请求：空仓 246/117/77/68/100ms，持仓 829/764/695/711/648ms。首次成本单列保留，未删除。

代码原因：`TrainingRunService` 的交互批处理规划在 `TOUCH_OR_TAPE_V2` 且存在交易依赖时返回无批处理方案；HEDGE 标记批处理也要求空账户。持仓需要逐基础事件做标记、成交、保证金和清算检查，因此 15m 展示推进会走 15 个 1m 内部边界。每波适配器提交、HEDGE 收尾和全局事件持久化反复发生，放大磁盘提交长尾；账户状态也反复构建。

逐事件计算不能简单跳过。可执行的下一轮设计应是：保留逐事件风控语义，将不可变状态构建结果在同一阶段内复用；研究以外部命令或有界内部批次暂存结果、在明确恢复边界原子提交领域事件、账户状态和全局记录。需覆盖订单触发、资金费、强平、取消、崩溃重启和命令幂等。这是有针对性的持久化重构，不是把 SQLite 的 FULL 调成 NORMAL，也不是直接跳到最终价格。

## 自动播放与呈现限制

三段均选择“1 展示 K/秒”。以下从播放按钮 click 到暂停按钮 click，统计暂停点击前主图数据中的展示条目增长；可能包含部分展示 K，不等同于精确收盘条数。

| 条件 | 实际采样时长 | 展示条目增长 | 约条目/秒 |
| --- | ---: | ---: | ---: |
| 开发，持仓 | 52.76s | 21 | 0.40 |
| 生产，持仓 | 44.62s | 16 | 0.36 |
| 生产，置前后空仓 | 38.94s | 38 | 0.98 |

前两段的窗口帧调度存在干扰，不能据此精确比较开发与生产播放吞吐；持仓路径的慢请求和独立服务计数是更强证据。

采样中发现 `document.visibilityState=visible`、`document.hasFocus()=true` 仍可能伴随约 1,004ms 的 rAF 间隔。调用 Page.bringToFront 后观察到约 4.2ms，后续记录也存在间歇性慢帧。因此本报告排除所有 `nextFrameMs` 的“真实绘制延迟”解读；原始数据保留，不把窗口调度异常伪装成应用掉帧。末段空仓播放接近目标频率，但仍不是屏幕逐帧验收。

工具的若干 locator 等待报告超时，随后 DOM 与 HTTP 确认成功；这些是工具等待异常，不计作应用失败。暂停后曾停在半根展示 K，下一次点击只完成该根，显示条目数没有增加；已修正采样器对“每次一定 +1”的假设，保留原始样本。
